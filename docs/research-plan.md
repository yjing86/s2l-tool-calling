# Can learning trajectories for function names and argument values improve data selection for tool-call fine-tuning?

**Research protocol · Revised November 23, 2026**

This document preserves the hypotheses, design choices and budget contingencies used to plan the study. The pilot measurement is identified below. The results report records which comparisons actually ran, their outcomes and the limits of the evidence. [Results](results.md) · [Experiment log](experiment-log.md) · [Paper guides](references.md) · [Token-level validation](field-loss-validation.md)

## Abstract

A language model that calls a tool must choose a function and supply the right arguments. A single wrong digit in an order ID can invalidate a call. In whole-answer loss, the weight given to that ID depends on its token count. We ask whether a small model can select more useful fine-tuning examples for a larger model by tracking the learning trajectories of function names and argument values separately.

A single Qwen3.5-0.8B proxy scores 4,000 Amazon Turnstile requests. Uniform random sampling (A), whole-answer trajectories (B) and separate field trajectories (C) each select 1,000 examples for a Qwen3.5-2B target with the same starting weights. The primary endpoint is **C minus B in request-level exact-call accuracy at equal target training tokens**. A further control (B′) averages the same name and value tokens as C into one score per checkpoint. It helps identify how much of the difference comes from excluding other tokens and how much from retaining separate trajectories. Secondary questions concern which argument errors change, transfer to an external tool benchmark, and accuracy after accounting for selection time. In the original single-call example at row 49, the unadapted proxy's mean losses were 0.094 for the whole answer, 0.009 for the name and 0.160 for the values. The original proposal treated target accuracy, selection gains and GPU cost as quantities to measure.

## Motivation

Suppose a user asks, “Track order 4821.” The output `cancel_order(order_id="4821")` copies the identifier correctly and chooses the wrong operation. The output `track_order(order_id="4812")` chooses the operation correctly and looks up a different order. Both earn zero for the request. Could a selection method with a limited training budget identify examples that cover these different failure modes?

Whole-answer loss averages over all supervised tokens. Each field's contribution is proportional to its token count. Parameter keys, markup and end markers also enter the denominator. In Turnstile row 49, the user asks for an exercise plan suited to their preferences. Of 78 supervised tokens, 6 belong to the function name, 12 to argument values and 60 to other positions. The unadapted proxy already predicts the name easily. The harder argument values account for only about 15% of the average. This observation motivates separate measurements. Their utility for selection must be tested on unseen requests. [Original row 49](https://huggingface.co/datasets/amazon/Turnstile-Synthetic-Domains/viewer/default/train?row=49)

## 1. Experimental arms

| Arm | How it selects 1,000 of 4,000 examples | Purpose |
|---|---|---|
| **A · Uniform random** | Sample uniformly without replacement. | Cheap, reproducible baseline. |
| **B · Whole-answer S2L** | Record one mean loss over all supervised reference-answer tokens at each of five checkpoints. Cluster the five-dimensional vectors and sample within clusters. | Direct adaptation of the whole-answer S2L approach. |
| **C · Separate fields** | Use the same requests, proxy and five checkpoints. Record one mean for names and one for argument values at each checkpoint. Apply B's sampling rule to ten-dimensional vectors. | **C−B is primary.** It measures the net change from the field representation. |
| **B′ · First additional control** | Use exactly C's name and value positions. Combine them into one token-weighted mean per checkpoint. | B′−B measures the effect of removing formatting and keys. C−B′ measures the gain from retaining two trajectories after restricting the token set. |

Within each paired seed, targets start from the same Qwen3.5-2B weights and LoRA initialization and learn **complete reference calls**. The unadapted 2B takes the same tests to measure the net gain from fine-tuning. The 0.8B model only provides selection signals.

## 3. How one proxy produces three loss measurements

1. **Train once.** Fine-tune the 0.8B model for one epoch on the full candidate pool with LoRA. Backpropagate the mean cross-entropy over **all supervised tokens in the complete reference answer**. The 2B arms use the same objective.
2. **Keep five checkpoints.** With 4,000 requests and effective batch size 16, there are about 250 optimizer updates. Score at 0, 10, 30, 80 and 250. For a run with T updates, use 0, round(0.04T), round(0.12T), round(0.32T) and T, and record the actual steps. Use the original weights at step 0 and the corresponding adapter over the same weights thereafter.
3. **Score every candidate at each checkpoint.** Freeze the proxy and teacher-force each reference sequence. Retain per-position cross-entropy using PyTorch. Compute three means on the same forward pass, over all supervised positions, over function-name tokens and over argument-value tokens. The full answer includes tags, parameter keys and delimiters. Field masks map spans to the actual tokenization and include scalar values in nested arguments.
4. **Validate alignment before scaling.** Read the training run's saved `args.json`. The effective ms-swift setting was `default+ignore_empty_think`; manually specifying `default` changes which positions receive labels. Compare input IDs, every target label and the whole-answer mean loss across training and scoring. Reload a saved adapter and confirm reproducible output on the same input. Five passes over 4,000 requests mean 20,000 example-level forward evaluations. For every request and checkpoint, save each field's loss sum and valid token count. B, B′, C and subsequent feature ablations reuse this record. [Verifier](../scripts/verify_tool_call_loss.py) · [Validation report](field-loss-validation.md)

Using the Hugging Face template and the unadapted 0.8B on CPU, row 49 gave mean teacher-forced cross-entropies of **0.093611** for the whole answer, **0.009124** for the function and **0.159913** for the values. All three come from one forward pass. They quantify reference-token predictability. The target's ability to produce a correct call independently is measured by generation. [Measurements](field-loss-validation.md)

Appendix B.3 of S2L records a loss every 500 iterations of Pythia-70M. Its main configuration uses 100 clusters and 20 clustering iterations. We use five measurements and ten clusters for the 4,000-request pool. Report clustering iteration limits separately from the number of random starts. The first paper guide discusses the authors' comparisons of trajectory length and sampling density. [Paper guide](references.md)

**Inspect the features before standardizing.** For each of C's ten raw columns, report the number of observed and missing values, variance, P10/P50/P90 and the fraction below 0.01. Report the corresponding distributions for B and B′. Keep missing argument values identifiable. Repeated forward passes on the same sample estimate numerical noise. Flag any column whose between-request variation is mostly within repeat error and check selection sensitivity with that column masked. Set constant columns to zero for the main analysis and standardize the others as prespecified. Use the candidate-pool statistics to assess whether name loss falls to near zero early. Row 49 alone cannot establish how often this occurs.

**Cluster and sample.** B uses five whole-answer means. C uses five name means and five value means. Standardize each feature to its own training-pool mean and standard deviation. Fit Euclidean K-means with ten clusters, ten initializations and the same clustering seed. Sample uniformly without replacement within clusters, aiming for equal quotas. If a small cluster is exhausted, distribute the outstanding slots in turn to clusters with remaining examples. Requests with no argument values form a separate stratum. B and C reserve identical slots proportional to its prevalence and use the same subset chosen there by name trajectories. When there are fewer than ten requests or distinct trajectories in a stratum, reduce its cluster count. Represent missing values as `null`. A remains uniform across the entire pool. Preserve unique IDs, answer lengths, tool frequencies, cluster sizes and subset overlaps. [S2L Algorithm 1](https://arxiv.org/html/2403.07384v2#S4)

**Calculate B′.** Suppose a request has two name tokens with mean loss 0.2 and eight value tokens with mean loss 1.0. B′ stores (2 × 0.2 + 8 × 1.0) / 10 = 0.84 for that checkpoint. C stores 0.2 and 1.0 separately. B′ has five features after five checkpoints. Use the same standardization procedure, cluster count, quotas and within-stratum seeds for B, B′ and C. All trajectory ablations reuse the no-argument subset. Generate the selected IDs on CPU and compare Jaccard overlap (intersection divided by union), tool coverage and length distributions. Downstream effects require target training and sealed evaluation. C−B′ jointly changes the relative influence of the fields and the number of dimensions.

## 4. Fair comparisons under two resource constraints

**Equal target training tokens.** Each target learns from its own 1,000 requests. To account for unequal sequence lengths, compute the pool-wide mean number of nonpadding tokens with the target tokenizer. The common budget is **2 × subset size × pool-wide mean nonpadding tokens per request**, approximately two passes over a typical subset. With 4,000 candidates and a subset of 1,000, multiply the mean by 2,000. With a 2,000/500 fallback, recompute the mean and multiply it by 1,000. Count prompt and answer tokens. Allow rounding of at most one optimizer update and record achieved total and answer-token counts separately for each arm. The budget can be computed before observing any selected sets or target performance. Save the checkpoint that first reaches it for every arm. After model lock, evaluate them on the same test. **The primary result is C's complete-call accuracy minus B's, in percentage points.**

**Equal deployment GPU time, budget permitting.** Measure throughput on the same GPU type, then set a common cap that allows all three arms to reach the token landmark. B and C can continue on their selected 1,000 examples after that point. A can continue with the same adapter and optimizer on random examples from the full 4,000, using the time saved by skipping selection. Report the number of distinct requests seen. This evaluates the entire deployment strategy. The equal-token comparison isolates the choice of training set more directly.

## 5. Scoring, uncertainty and interpretation

**Three fixed training seeds.** Calculate C−B on the same held-out request groups for each seed. Report the mean difference and between-seed sample standard deviation. In each of 2,000 bootstrap draws, use the same resampled groups for all methods and all seeds. The interval describes variation across test groups conditional on these trained models. Three model predictions of the same request still correspond to one test request.

**Exploratory argument errors, registered after the pilot and before opening the sealed test.** Keep strict structural matching for the primary endpoint. Attach the following diagnostic labels to frozen predictions, preserving the evidence and denominator for every flag. A unit-conversion error requires a target unit explicit in the schema, a different unit in the request and a deterministic conversion to the reference. Flag a predicted quantity that disagrees with that conversion. Treat case-only changes, omitted optional empty arrays and array-order differences as separate candidate representation differences. Label a candidate semantically equivalent only where the tool specification establishes equivalence. Leave unsupported case and ordering changes unresolved. A type-only difference remains a type error. Count parsing failures that reach the generation cap. Freeze rules and tool-specific equivalences before opening the outputs. All pilot/test examples and labels stay on the evaluation side.

**Primary metric.** Give the model the request, date and candidate tools. Generate independently once. A parse failure, missed or extra call, wrong function, or incorrect argument type or value earns zero and stays in the denominator. Object-key order is immaterial. The general matching policy permits reordering independent calls while preserving their multiplicities and ordered array contents. This study's main task requires exactly one call. Fix accepted representations, tool names, counts, argument keys and values before opening the test. Calling a cancellation tool for order 4821 and tracking order 4812 both fail, with different error types.

**Planned value-source annotations.** Assign each reference scalar leaf one source using the request and reference call. A request can contain several categories. Record tool family, token count and nesting depth. Freeze the rules before inspecting predictions. Two team members independently annotate a common random sample, report its size, agreement and disagreements, and adjudicate before seeing B/C outputs. Analyses requiring these labels depend on the availability of reviewed annotations.

| Source | Operational criterion | Example |
|---|---|---|
| Directly stated | The request gives the same value, and its field identity is unambiguous in context. | “Track order 4821” supplies the string `4821`. |
| Normalized | A predefined mapping expresses the same information in the required form. | “Four items” becomes integer 4, or a fully specified calendar date becomes ISO format. |
| Derived | The value must be calculated from the system date, a given time zone, multiple inputs or an explicit rule. | Resolve “next Tuesday” using the supplied system date. |
| Indeterminate | A reference date is missing, the field is ambiguous or the value requires outside facts. | Relative time without a reference date. Report the count separately and retain the request in the overall denominator. |

For selected training sets, report leaf counts and request counts per category, tool frequencies, answer-length distributions and B/C subset overlap. On the test set, record the first failure per request (parse, count, function, arguments, correct). Distinguish missing/extra keys, types and values in argument diagnostics. For each value category report both of the following.

1. Among **all requests containing that category**, count success when the tool and call count are correct and every reference leaf of that category is correct.
2. Among the **same requests on which both B and C get the tool and call count right and the category is present**, compare the proportions with every leaf of that category correct.

Match tools by name and leaves by reference path and type. A missing leaf, wrong type or wrong value fails. Extra fields fail the complete request. Also report correct leaves/reference leaves and state each denominator. Use paired resampling by request group for intervals, preserving within-request dependence across leaves.

**Model lock.** Before viewing formal predictions, use measured pilot timings to record the arms and seeds admitted by budget. Freeze matched-token checkpoints. Use development scores alone to choose any equal-time endpoints. Run one complete A/B/C round for each seed in order, 42, 43 and 44. All three rounds require nine target fits. If the budget permits only one or two full rounds, report the three or six completed fits and limit across-seed claims accordingly. B′ at seed 42 is the tenth fit if resources allow. Within a round, methods share target initialization seed and trajectory arms share selection seed. Record the selection, initialization, data-order, clustering and proxy seeds separately. Reusing the same split and proxy leaves uncertainty about sensitivity to proxy training randomness. Open the tests only after locking models, scoring code and seed manifest. Reuse predictions for identical checkpoints.

Report correct and total counts for each arm, and counts of “only C correct” and “only B correct” for each seed. **C−B (percentage points) = 100 × (only C correct − only B correct) / total requests.** Resample near-duplicate groups 2,000 times with paired predictions intact and report a percentile 95% interval. Present each seed and the mean and range. B−A, C−A, B′ and error slices are secondary results. Report uncertainty for small slices and sign changes across seeds. Remaining development examples can diagnose whether a field's loss predicts its errors.

| Possible outcome | Interpretation |
|---|---|
| C answers more requests correctly than B, with fewer argument errors on requests where both chose the correct tool. | Under these data, models and LoRA settings, field information improves selection. Argument generation may account for some of the gain. Check seeds, length and tool coverage. |
| Field loss identifies failure modes, and B and C achieve similar downstream scores. | The signal may be diagnostically valuable without a clear complete-call gain for the selected data. |
| C leads at equal tokens, and A catches up or surpasses C at equal total GPU time. | Selection improves performance per target training token. For a single target fit its overhead can offset this gain. |
| Random leads, rankings change across seeds or the pilot approaches the ceiling. | Report effects, intervals, remaining headroom and representative failures to characterize the strength of the evidence. |

**External evaluation.** Train only on the Turnstile candidate pool. Prespecify BFCL v4 Non-Live single-turn `simple_python` (one tool) and `multiple` (several candidate tools, one call required). An independent two-call follow-up could freeze `parallel_multiple`. Use up to 100 requests per category. For each request, join seed 31415, category and official ID with vertical bars, SHA-256 hash the UTF-8 bytes, sort ascending by hash with ID as tiebreaker and take the first 100, or all if fewer. Freeze IDs, dataset/scorer commit, template, output cap and decoding configuration. ## 7. Decision to extend the study

Register the primary outcome, external manifest, budget order and decision rules before unsealing. A difference of +2 percentage points was the team's threshold for spending additional GPU time. This means 40 net extra correct answers out of 2,000, or 30 out of 1,500. With independent requests and similar discordance rates, interval widths scale approximately as 1/√N. Increasing the test from 800 to 2,000 would narrow the interval by about 37%. Use paired group resampling for the actual interval. The spending threshold by itself gives no power guarantee.

| Evidence from the course pilot | Action and interpretation |
|---|---|
| At prespecified seed 42, matched-token C−B is at least +2 percentage points and the lower bound of the paired 95% interval exceeds zero. | Prioritize independent seeds and unopened external samples. Treat a single training seed as preliminary, then check the remaining prespecified seeds before expanding to a second model or dataset. |
| The primary gate fails, but C's **derived-leaf error rate** is lower than B's for at least two prespecified paired seeds. | Among requests where both models produce the correct tool and count, report errors per reference derived leaf, number of requests and paired group intervals for every seed. Also report end-to-end accuracy on all requests with such values and joint coverage. If the end-to-end direction reverses or a rerun has no comparable derived leaves, keep the conclusions descriptive. Where comparable data exist, use interval width to assess support for an independent check. This route warrants only a small independent replication. |
| Field gains do not repeat, seed directions disagree or intervals still contain meaningful effects in both directions. | Publish the complete pilot. Distinguish a small effect, imprecision, limited base-model headroom and costs offsetting the gains. New data can test conditions for failure. A claim of equivalence requires a prespecified equivalence margin and a sufficiently narrow interval. |

The first opening of the internal test provides course-pilot evidence. Evaluate any new rule suggested by its results on a new sealed sample. An external item whose score is known can support repeat benchmarking. An independent replication needs reserved, unopened IDs within each category or independently authored evaluation items. Report every prespecified seed and denominator.

### 7.1 Additional controls and the questions they address

**Preregistered exploratory full-pool reference.** At seed 42, train the 2B on all 4,000 candidates for about two passes with the main LoRA settings, optimizer and template. Save a checkpoint immediately at the main token budget. It distinguishes the effect of covering more requests from the effect of training on more total tokens. Label the matched-budget, final (approximately two passes) and development-selected checkpoints separately. Test results play no role in selection. This reference follows the primary study in the queue and runs only if the measured time remaining covers its forecast plus 30% and a ten-minute reserve.

| Control and procedure | Question |
|---|---|
| Tool-stratified random selection. Stratify by the reference function name, allocate slots in proportion to the original pool using largest remainders and sample randomly within strata. | Does C beat a cheap strategy that preserves the original tool frequencies? Also inspect composition at comparable argument lengths. |
| B′, pooled name/value loss at five checkpoints. | B′−B measures what changes when all other positions are removed. C−B′ measures the additional change from retaining separate trajectories. |
| Values only at five checkpoints. Separately, name/value losses at the final checkpoint only. Apply the same standardization and sampling in each case. | The former tests the incremental contribution of the name trajectory. The latter tests earlier dynamics against a single snapshot. |
| A full-pool 2B reference. Save matched-token, final and development-best checkpoints as specified above. Record the associated times. | What does broader coverage buy at roughly matched training volume? What further accuracy does the larger full-data budget buy? |
| Model-estimated difficulty. Freeze the 0.8B checkpoint and decoding configuration. Generate four candidates per request, estimate difficulty from tool and argument matches and sample 1,000 requests stratified by difficulty. | Compare with a static baseline inspired by ToolACE-R. Document the omission of iterative retraining and data expansion, and charge the generation cost. [ToolACE-R method](https://arxiv.org/html/2504.01400v2#S3) |
| Hidden-state probe. Give each request one score using the protocol below, select 1,000 and train the target on the original references. | Does the added hidden-state signal improve downstream selection enough to justify its generation and fitting costs? |

**Authorized exploratory crossed-seed diagnostic.** The first two matched-token runs had opposite C−B signs on development. The main experiment measures the variability of the complete selection-and-training procedure. To diagnose these two rounds, reuse the saved B/C subsets while crossing selection seed and target training seed. The existing cells are (42,42) and (43,43), ordered as (selection, training). Add (42,43) and (43,42) for both B and C, or four extra 2B fits. Keep the base weights, optimizer and token budget fixed. Evaluate the final checkpoint on the same 400 development requests. Compare C−B across all four cells, holding either the selected sets or training seed fixed. This exploratory diagnostic was triggered by development scores. Two levels per factor describe sensitivity for these particular rounds. Initial measured timings implied about 64 minutes for four fits and 14–17 more minutes for four endpoint evaluations. Deduct the actual primary and full-reference occupancy and their reservations from the original 20 GPU-hours. Admit this diagnostic only if the remaining budget covers 1.30 times the updated four-fit-plus-evaluation estimate, plus ten minutes. Record queue admission and actual start separately.

### 7.2 Fair comparison with a hidden-state probe

1. **Generate and label.** Freeze the same final 0.8B snapshot. Generate four answers for each training candidate under prespecified temperature, seed, count and output cap. Reuse the difficulty baseline's generations where applicable. Read the hidden state immediately before the start of each generated argument value. Use the training-side reference to label correctness of its function, argument path, type and value. Record extra generated tokens, GPU time, unparsable fraction and label counts.
2. **Cross-fit within the training pool.** Split near-duplicate request groups into five folds with every candidate and field of a request kept together. Fit logistic regression on labeled generated values from four folds, then apply it to the held-out fold. Prespecify layer and regularization. If tuning is needed, perform internal cross-validation only within the four fitting folds. Combine the out-of-fold predictions so each request receives a score from a probe fitted without its labels. Only training-pool data enter any fold. All methods share the frozen proxy that previously trained on this pool.
3. **Separate discrimination from downstream selection.** On the same labelable held-out generated values, use a correct value as the positive class. Compare the probe probability with mean token log probability for that value. Report AUROC, average precision, positive prevalence and effective field count, alongside the number of values with no valid pair. For downstream selection, average predicted value-correctness probabilities within each generated call. Assign zero to a parse failure, an unlisted tool, missing schema-required fields, a violation of the selected tool's explicit type or extra-field constraints, or an argument-bearing candidate without a usable score. A schema-valid tool that differs from the reference does not trigger structural zeroing. Selection scores use only the generation, tool specification and out-of-fold probe. References supply probe-training labels and out-of-fold diagnostic metrics. Average over the four generated calls per request, cluster and sample across clusters using the same procedure on these one-dimensional scores. Reuse the common no-argument quota and subset. For the target, train on the original references with the same token budget and blinded evaluation. Report standalone training, scoring and inference GPU time for each route.
4. **Interpretation.** This comparison assumes existing reference calls and asks which requests should receive target training. The original probe paper also filters self-generated answers for unlabeled requests, which provides a different training resource. A gain in value-correctness discrimination can coexist with similar downstream complete-call accuracy. Report labeling source, training cost and end result for both methods. [Original method, §§4.1–4.2](https://arxiv.org/html/2608.03071v1#S4)
